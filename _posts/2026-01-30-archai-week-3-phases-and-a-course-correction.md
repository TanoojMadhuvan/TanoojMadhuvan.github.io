Deploy pressed, and Gemini started proposing and running its own phases
against the ranges from Week 2. The results below are real gem5 trial
output, not projected — and the most useful moment this week wasn't a clean
result at all, it was catching a wrong assumption before it shaped a phase.

## Phase 1: does L1 instruction cache size actually matter here

<figure>
  <img src="/assets/images/archai/archai-phase1-l1i-results.jpg" alt="ARCHAI dashboard Testing tab: 'Running Phase 1 Trial 4, Concept: Evaluate L1I capacity requirements for recursive kernels and library overhead', with two charts — Simulation Runtime vs l1i_size dropping from about 0.000215s at 1kB to about 0.000198s by 4kB and flattening, and DDR Memory Usage vs l1i_size staying roughly flat around 226-227kB">
  <figcaption>Phase 1, live: simulated runtime drops as <code>l1i_size</code> grows from 1kB to 4kB, then flattens — DDR usage stays essentially unchanged throughout.</figcaption>
</figure>

The phase's own stated reasoning, carried over from an earlier Phase 0:
"L1D increases beyond 16kB actually reduced the instruction rate without
improving execution time, suggesting the working set is tiny; Phase 1 will
determine if a minimal 1kB L1I is sufficient or if instruction fetch latency
is the true bottleneck." The chart answers that directly — simulated runtime
keeps dropping as `l1i_size` grows from 1kB toward 4kB, then goes flat. Below
4kB, something is actually costing cycles; above it, more L1I buys nothing.

## Phase 2: does DDR capacity matter at all, given how small this workload is

<figure>
  <img src="/assets/images/archai/archai-phase2-ddr-results.jpg" alt="ARCHAI dashboard Testing tab: 'Running Phase 2 Trial 1, Concept: Analyze the impact of DDR capacity on execution speed given the small process footprint', with charts showing a single data point at 16MB DDR (Sim Time about 0.0001975s, DDR Memory Usage about 211000 bytes), and below it a validation paragraph"
>
  <figcaption>Phase 2's premise, stated up front: the workload uses ~226KB — orders of magnitude below even the smallest DDR size on the table — so scaling DDR capacity should change nothing.</figcaption>
</figure>

The hypothesis going in: "Trial data from Phase 0 indicates that 'Used Memory
Bytes' is approximately 226KB, which is orders of magnitude smaller than the
minimum 16MB DDR size; I expect that increasing DDR capacity to 64MB will
yield no change in Sim Secs, confirming that memory capacity is not a
bottleneck." After the trials ran, the dashboard's own validation text:

> I validated that the Phase 2 results showed identical 0.000198s execution
> times across all DDR sizes, which confirmed my hypothesis that memory
> capacity is not a bottleneck for this 226KB footprint. In response, I
> updated the Phase 3 hypothesis to use this static baseline to investigate
> if increasing the core count provides any benefit to what appears to be a
> strictly sequential execution flow. Appropriately matching hardware
> resource allocation to the software's actual working set and threading
> model prevents wasted silicon area and minimizes the power-delay product
> of the final design.

That's a real negative result treated as useful information, not a dead end —
exactly the point of testing a hypothesis instead of assuming it. It also
sets up Phase 3 correctly: if the workload is genuinely sequential, adding
cores should not help, and the phase gets framed to test that directly.

## A hypothesis that didn't match the actual code

<figure>
  <img src="/assets/images/archai/archai-phase-hypotheses-modification.jpg" alt="ARCHAI dashboard showing Phase 2 and Phase 3 hypothesis text, and below it a free-text 'Enter modifications' box containing the typed note: Since this program is multithreaded, I think that changing the number of cores earlier can quickly resolve bottlenecks, with a Generate / Modify button">
  <figcaption>Phase 3's own hypothesis (correctly): the stressor is single-threaded, so more cores shouldn't help. The modification box beneath it claims the opposite.</figcaption>
</figure>

Phase 3's hypothesis, generated by Gemini: "Since the current stressor is a
single-threaded sequential program, increasing the number of cores from 1 to
3 will not improve execution time and will likely decrease overall
efficiency due to resource contention or overhead." That statement is
correct — `uarch_stressor.c` (Week 2) has no threading of any kind, no
`pthread`, no OpenMP, just three sorts running one after another on one
thread.

The modification typed into the box directly underneath it says the
opposite: "Since this program is multithreaded, I think that changing the
number of cores earlier can quickly resolve bottlenecks." Going back to the
actual source settles which claim is right — the stressor is not
multithreaded, so Gemini's own hypothesis was the one grounded in the real
workload, not the human note proposing to act on the reverse assumption.

Worth being direct about why this is worth a whole section rather than a
footnote: an autonomous loop like this doesn't remove the need to check
claims against the actual artifact, it just moves *where* the wrong
assumption can enter. Here it entered through the human side of the
human-in-the-loop design, not the model side — which is exactly the
failure mode a "human can override anything" input box is supposed to catch,
not necessarily immune to. Whether this particular note got acted on or
corrected before Phase 3 actually ran isn't something this week's artifacts
settle — but the discrepancy itself was worth catching before trusting either
version blindly.
